# 项目哲学

Rebuild Any Web 把复刻看作持续发现和重建用户可观察体验的过程。Codex 是执行者；RSI 帮助改进探索；E2E 保存模具；Goal 保持目标和持续执行。

## 探索要改变方法

探索从真实状态、动作和结果出发。历史的用途是帮助决定下一步：哪里尚未访问、哪个假设被推翻、哪种采集方法漏了需求。只修已有测试会在已知范围内循环；发现遗漏有时需要改变观察对象或输入方式，而不是再运行一次相同探针。

RSI 使探索策略本身成为改进对象：保存真实探索树，在同一历史池回放不同可执行策略，根据反馈修订，再实际部署。一次反思或重跑已有测试不等于完成这条闭环。Duolingo 的真实发现已为改进它提供依据；先完成复刻与完整验收，再在优化阶段用消融判断机制如何保留、调整或简化。执行顺序由 [Workflow](../workflows/rebuild/WORKFLOW.md)维护，原论文与既有实验见 [研究来源](RESEARCH.md)。

## E2E 是可执行的复刻模具

模具把已发现需求转成可重放的状态准备、场景、平台动作和断言。另一种语言可以改变内部结构，但用户看到的内容、业务关系和前端体验应满足同一要求。文档记录理由与未知，运行模具重建已覆盖需求的完成状态。

主页、布局、字体、素材、交互、动效、声音和进度恢复从第一轮属于模具。它们不能留到业务通过以后补，也不能被核心测试、结构相似或程序启动代替。原版不可重置或动态内容无法对齐时保留具体限制，下一步针对缺口补方法。

## Goal 保持方向

Goal 保存本次目标与完成条件，workflow 保存执行方法，项目配置连接模具和工具。每轮由用户目标与实际缺口决定先探索还是先实现；批次服务工作安排，不自动成为缩小产品范围的决定。

原生 Goal 推动 Codex 持续执行，工具提供实际反馈。持续运行的价值是目标差异逐渐收敛，不是运行时间、题数、断言数或文档数量增加。真正需要外部输入时交接；用户结束试验后停止案例工作。

## 观察与判断分开

驱动返回实际事实，统一断言判断结果。原版 API、DOM、图像和音频相互印证，不让候选自己的实现成为原版规则证据。保留假设被推翻的过程，不以挑选有利读数消除矛盾。

已有测试全通过说明已有要求得到满足，不能证明未知不存在。完成判断回到用户目标、主要用户旅程与实际差异，未知和未覆盖继续可见。

## 简单机制服务真实消费者

优先连接已有观察器、模具和驱动。RSI 的历史池保存真实世界与策略选择证据，原生 Goal 拥有的任务状态和持续运行职责不在仓库重复实现；兼容宿主适配按实际需要启用。每个新工具应解决一个已出现的失败，并有可执行消费者。

[Duolingo 实践复盘](DUOLINGO-LESSONS.md)保存这些原则的具体来源；批次证据留在案例与历史，不继续追加到哲学中。
