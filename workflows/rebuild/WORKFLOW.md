# Codex App 重建工作流

在当前 Codex 中执行：**RSI 探索，E2E 复刻，原生 Goal 持续推进。** 用户目标决定完成条件；本工作流决定如何利用真实反馈行动。Duolingo 已结束的实践经验见 [复盘](../../docs/DUOLINGO-LESSONS.md)，新的消融实验不是工作前提。

## 连接项目与 Goal

1. 从用户要求确认原版入口、目标平台和一致性要求。已有项目读取 `rebuild.json`；新项目按 [项目入口](PROJECT.md) 建立一份配置，尚未探索的输入可以暂不填写。
2. 用 `project preflight` 检查 RSI 与共同 E2E 的方法接线，再用 `project status` 读取模具、历史与入口；检查结果所对应的源码／二进制。缺口先进入本轮行动，历史结果仅用于选择下一步，不等于当前通过。
3. 用户明确要求创建 Goal 时运行 `project goal`，把输出 JSON 交给原生 `create_goal`。已有同目标 Goal 时读取并接续；目标改变先按宿主能力处理，不另写当前 GOAL 文件或重复启动任务。
4. 用户没有要求创建 Goal 时仍可按本流程完成已授权工作。原生 Goal 模式不安装 Harness、不启 `exploration_start`；旧 Stop Hook 已删除。

“开始／继续复刻”默认包含真实 RSI 链路，不等用户另行要求接入。第一条业务探索探针前先确定它使用的固定协议与 collect 入口；若正在修登录、状态恢复或观察器，明确记录为准备，准备可用后立即从真实 collect 开始。不能先持续手动探索，再将已有结果补写成 RSI 历史；后续策略比较与实际再部署按下文接续。

```sh
python3 -m workflows.rebuild.project preflight --workspace <工作区> --project <rebuild.json>
python3 -m workflows.rebuild.project status --workspace <工作区> --project <rebuild.json>
python3 -m workflows.rebuild.project goal --workspace <工作区> --project <rebuild.json>
```

用户修订范围时，先同步项目配置的目标与完成条件，并保留修订来源；当前用户要求优先于已创建 Goal 的旧正文。宿主若不能编辑活动 Goal 正文，明确报告限制，不能把未完成目标标为完成来重建。数据抽样、范围缩减或其他例外只影响用户明确豁免的维度，不自动豁免业务、视觉或持久化。

Goal 模板在 [GOAL.template.md](GOAL.template.md)，只提供目标、完成条件和方法连接。项目配置提供案例值；原生 Goal 工具管理生命周期。CLI 不调用模型，也不自行创建 Goal 或设置预算。

## 每轮选择：探索还是实现

先读取目标、当前用户旅程、已发现需求、实际差异和仍未知的分支，并重新运行 `project preflight`。RSI 配置、真实池、完整池策略比较或再部署缺失时，先补可恢复状态及驱动，再实际 collect／replay／collect --pool，把发现接入共同 E2E。首次准备可以探查入口、修采集器，不能长期以准备为由绕过方法。检查只读、不启动探索，也不阻止修复所需的构建命令；接线齐全不证明目标完成。选择能让目标体验收敛的下一步：

| 现场反馈 | 下一步 |
| --- | --- |
| 主页、导航、声音或主要旅程缺失 | 优先补完整体验及其模具，避免继续扩题数或修无关小问题 |
| 候选明显不同，模具却通过 | 回到原版检查漏验维度，先补能检测差异的要求 |
| 原版证据明确，候选不符合 | 保持要求，修实现后实际复验 |
| 观察器漏控件、截图矛盾、题目身份变动 | 修观察方法并回原版验证，保留原失败 |
| 现有场景通过但仍有未知或未访问入口 | 选择能揭示遗漏的探针，不能据局部通过完成 Goal |

选择前对照完整用户旅程说明本轮解决哪个已知失败或未知分支；局部模具变绿后，回到主要旅程缺口选择下一步。不要因短小固定探针容易得分而长期停留在同一局部功能，也不要仅为一个小控件复制整套固定协议。能接续同一协议的历史时接续；观察、恢复或评价语义确实改变时才另开协议。

一次选择可以是补观察、修采集器、扩模具或修产品，不要求每轮先走完整固定阶段。批次安排不缩小用户目标；没有页面层数公式、六类检查填表或必须新增一条行为的探索配额。

## 用 RSI 改进探索

RSI 使用 [历史树回放与策略改进接口](RSI.md)。准备可恢复的原版状态和固定发现／评价命令，保存实际探索树；用 `replay` 在全部历史世界上比较当前策略与修订版，再把胜出策略通过 `collect --pool` 部署到下一轮。默认由当前 Codex 读取回放反馈、改写可执行策略；已有固定 developer 命令时可显式运行 `cycle`。项目 `inputs.rsi_config` 与 `commands.rsi_collect/rsi_replay` 连接这些调用，不由旧的一层实验脚本代替。

原生 UI 的加载就绪、恢复、AX 解析和调用生命周期按 [RSI 的协议准备要求](RSI.md#原生-ui-协议准备)处理。观察器有反例时，先用已保存原文验证修订，再冻结新协议；不能靠一轮轮真实 collect 重复试错本可离线发现的解析问题。

首次探索可以先建立 seed、观察器及策略，已有零散历史不能凭空补成可恢复的树。每次修订读取真实轨迹和评分；所有候选在同一冻结池评价，原策略保留。原版会话无法恢复时记录原因并先修准备方法，不能把浏览器源码快照称为远程状态恢复。

原生控制若只能跟随前台窗口，来源守卫通过只证明当次页面正确，不能证明持续独占。外部页面切换使守卫中断时，保留实际终态与部分回执，区分运行环境不可用和业务要求不满足；不要把中断世界并入完成池。确认目标绑定可用，或安排浏览器空闲时段后再部署，不能靠反复重启整个 collect 争抢前台。移动到独立窗口也须实测是否仍跟随前台；绑定 API 不可用时记录具体能力限制。原生 Goal 可以继续已授权且不依赖该窗口的实现与验证，不另启续跑器、不把失败改为通过。

读取实际历史和候选差异，提出能区分解释的探针。优先关注主旅程缺口、无法被现有模具解释的差异以及观察器盲区。策略需要变化时记录它依据的反馈、下一步假设和实际执行结果；复用案例已有历史／反馈文件，无需新管理系统。

探索包括控件内外的内容：悬停／点击／焦点／键盘、滚动与遮挡、退出恢复、跨页状态、Canvas／CSS背景、媒体播放及题间状态。当前视口、ARIA角色或接口题单都可能不完整。输入方式分别记录；没有记录的方式保持未知，不回填成通过。

执行探针后保存原版状态、动作、结果及证据，检验假设。发现影响实现的需求时进入模具；没有新发现时保留结果，按反馈改变方法或转向更重要缺口，不为计数制造新行为。frontier 只列出已观察动作，Codex 还要主动寻找它尚未识别的入口。

浏览器探针可使用[采集 CLI](../../docs/BROWSER-CAPTURE.md)，把实际 receipt 写入本次 RSI workspace。Codex 从原版观察选择能排除旧数据的显式 ready 条件；动作执行后按步采集，并保留未请求、失败和状态漂移。requirement 引用原版步骤证据后，已有 frontend 比较器对候选强制核验同名状态、文件摘要及共同准备条件，再执行原断言。采集不接收期望答案，不自动修订模子，也不替代完整发现／评价／回放／再部署链路。

## 用 E2E 建立并消费模具

每条用户需求连接共同前置状态、动作、期望和证据。两端分别适配 UI，驱动返回事实，由共同断言判定。从第一批完整旅程起，同时覆盖业务、内容、主页、布局、字体、素材、交互、动效、声音和持久化。

- 保存原版版本／日期、准备路径及重置边界；线上刷新不是远程状态重置。Tab 自动滚动、鼠标悬停提示、焦点框、日期与加载状态都是比较前置条件。状态不一致时保留原始像素结果，单独报告不可比原因并修准备；不能把该结果直接解释为实现质量，也不能用事后遮罩抹掉差异。
- 在实际原版或明确固定参考确认要求后冻结实现批次。新发现进入下一修订；产品原规则确需修正时保留反例及旧版本，不偷偷放宽标准。
- 先构建候选再驱动实际 UI；记录实际二进制与动作。API 或资源文件存在不证明界面和声音已被消费。
- 分开报告知识来源和 pass/fail/not_run/unavailable。核心、几何、整图与音频各自是测量，按用户需求组织结果，不能相互替代。

既有业务协议及参考确认／冻结命令见 [BEHAVIOR-CONTRACT](../../docs/BEHAVIOR-CONTRACT.md)；前端比较由 `capabilities.rebuild.frontend` 执行。案例命令从同一项目入口调用，失败退出码保留：

```sh
python3 -m workflows.rebuild.project run --workspace <工作区> --project <rebuild.json> --command replay --out artifacts/replay-new
python3 -m workflows.rebuild.project run --workspace <工作区> --project <rebuild.json> --command compare --observed artifacts/replay-new/observed.json --out artifacts/compare-new
```

## 接续与完成

每轮结束把实际观察、契约修订与验证结果存到其拥有的案例路径；下一轮重新读取目标和证据，再选择行动。不要在 README、哲学或架构追加本轮进展，也不要复制原生 Goal 的当前状态。

按用户目标检查主要旅程、体验差异和未知，交付可运行实现、复跑入口及需求级结果。已有测试全通过、记录队列为空或旧 Pipeline complete 都不能单独完成复刻 Goal。

用户结束案例试验时，按宿主规则停止持续执行；案例结论记录已交付、已验证、失败、未知、用户范围例外与私有输入依赖，不把“停止”记成“完成”。若同时授权预览或复盘，完成这些收尾，不恢复原版探索；提供候选的明确启动入口，检查冷启动、认证和所需业务依赖；端口开放或健康接口通过不证明依赖可用。启动检查不充当共同 E2E。

用户要求人类观看的 E2E 预览时，以普通速度操作真实候选，显示鼠标位置、点击及输入焦点；先滚动到目标并停稳，再执行动作。使用实际可见窗口检查说明、暂停控件和业务目标，不用超出窗口的模拟视口判断可见性。采集截图不能使播放反复缩放；功能断言和人类观看效果分别验证。失败停在现场，结束后保留手动查看入口；预览结果不替代两端共同验收。

用户明确停止后结束相应工作。真正需要外部输入时遵循宿主交接／blocked／恢复规则，不靠自动续跑猜测授权。已结束案例只用于提炼经验，除非用户明确要求重新开始。

旧 Stop Hook 已删除。手动 MCP 验证工具与固定批次 Pipeline 保留给显式调用，使用边界见 [兼容说明](../harness/WORKFLOW.md)；它们不负责自动续跑，不把旧阶段配额引入原生 Goal 路径。

## 完成后的优化

先完成用户要求的复刻、业务与前端验收，交付可运行基线；进入优化阶段后再使用消融。消融用于判断哪些机制值得保留、调整或简化，以及怎样降低成本和耗时，不作为探索、实现或完整验收之前的步骤。

优化时固定已完成的基线与同一套验收，逐项移除机制，比较体验质量、成本和耗时，保留实际结果。仍有目标功能或体验缺口时先回到复刻闭环，不将未完成工作记成优化。
